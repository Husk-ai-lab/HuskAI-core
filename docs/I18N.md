# Internationalisation (i18n)

Oct 3, 2026 · @Marco

Husk speaks **English (default)** and **Italian**. Every user-facing string comes from one shared catalogue used by both backend and frontend.

```text
app/i18n/
  __init__.py        t(key, lang, **params), resolve_lang(), language_name()
  errors.py          LocalizedError, api_error(), request_lang(), render()
  locales/en.json    source of truth for keys
  locales/it.json
app/frontend/src/i18n/index.tsx   I18nProvider, useI18n()/useT(), translate(), detectLang(), fmtDate…
```

Supported languages and the default are in `app/config.py` (`SUPPORTED_LANGUAGES`, `DEFAULT_LANGUAGE`).

## Keys and format

- **Flat, dot-namespaced keys:** `login.title`, `errors.document_not_found`, `discovery.steps.extract`, `enums.priority.alta`.
- **Placeholders** use `{name}`: `t("chat.selected", label="Analisi")`.
- **Plurals** use `key_one` / `key_other` and a `count` param (i18next convention). The frontend picks the form with `Intl.PluralRules`; the backend uses the CLDR rule for en/it (one when n == 1).
- **Fallback:** requested language → English → the key itself, so a missing key is visible, never a crash.
- A param given as `{"en": "...", "it": "..."}` resolves to the target language. This is used for content that already arrives translated, such as Neon maintenance messages.

## Which language is used where

| Situation | Language |
| --- | --- |
| Before login (login page, maintenance screen, startup alert) | Saved choice in the browser (`husk.lang`) → browser language (`it*` → Italian) → English |
| First access after login | The browser-detected language stays until the user changes it in Settings (saved to `user_settings.language`) |
| After that | `user_settings.language`, changeable any time in Settings → Language |
| API error messages | `Accept-Language` sent by the UI on every request; the response carries `detail` (translated) + `code` (stable key) + `params` |
| Agent output (notes, facts, opportunities, automation labels, chat replies, run logs) | The acting user's language. Agent instructions are English, with `agent.write_in` appended ("Write all user-facing text … in Italian") |
| Desktop maintenance notification | Language of the last signed-in user |

Content that agents or users created earlier (automation titles, chat history) stays in the language it was written in.

## Rules for contributors

1. **Never hard-code user-facing text.** Backend: `t(...)`, `api_error(status, "errors.x")` or a `LocalizedError("errors.x")`. Frontend: `useT()` / `useI18n()`.
2. **Add the key to `en.json` and `it.json` together.** Tests fail on a missing key, a key used in code but not defined, or mismatched `{placeholders}`.
3. A frontend guard (`src/test/i18n.test.tsx`) parses every `.tsx` with the TypeScript compiler and fails on JSX text, or `placeholder` / `title` / `aria-label` / `alt` literals, containing letters. Brand names are allow-listed.
4. **Stored enum values stay as they are** (`bozza`, `alta`, `vero`, `modello`…): they're data ids. Show them through `enums.<enum>.<value>` keys.
5. Assert on `code`, not on translated `detail`, in tests and in client logic.

## Adding a language

1. Copy `app/i18n/locales/en.json` to `xx.json` and translate every value (keep `{placeholders}`; add `_one` / `_other` plural forms where the language needs them, and extend `_plural_suffix` in `app/i18n/__init__.py` for languages with more plural categories).
2. Add `"xx"` to `SUPPORTED_LANGUAGES` in `app/config.py`, and add a `Language` member in `app/data/models/user.py`. Then add the import, `SUPPORTED`, `LANGUAGE_LABELS` and `LOCALES` entries in `src/i18n/index.tsx`, and `LANGUAGE_NAMES` / `LOCALES` in `app/i18n/__init__.py`.
3. If Neon maintenance messages should exist in that language, add a `message_xx` column (a technical-plan change); otherwise the English message is shown.
4. Run `uv run pytest test/test_i18n.py` and `npm test`.
